# Diabetes Risk Screening Model

> ## ⚠️ NOT CLINICALLY VALIDATED — DO NOT USE FOR MEDICAL DECISIONS
>
> **The training labels in this project are synthetic.** They were generated by a
> hand-written logistic risk formula plus random noise (see
> `src/generate_screening_data.py`), not observed from real patients.
>
> Consequences you must understand before reading any number in this repo:
>
> - Reported metrics (ROC-AUC ≈ 0.81) measure how well the model **recovers a
>   formula someone wrote**. They say nothing about real diabetes risk.
> - Logistic Regression "beating" XGBoost is **circular** — the data-generating
>   process is itself logistic. That result does not transfer to real data.
> - The 100,000 row count is a parameter of a `np.random` call, not evidence of
>   statistical power.
>
> This is an **engineering and methodology demonstration**. It is not a medical
> device, not a diagnostic tool, and must not inform anyone's health decisions.
> On real clinical data, expect AUC in the 0.70–0.78 range, which is where
> validated instruments like FINDRISC and the ADA risk test actually land on
> these features.

## Overview

A diabetes risk screening model over 7 self-reportable inputs, with calibrated
probabilities and Low/Medium/High risk stratification, served through a Flask
web interface.

**Inputs (7):** age, gender, BMI, hypertension, heart disease, diet, physical
activity.

**Deliberately excluded:** `HbA1c_level` and `blood_glucose_level`. These are
diagnostic biomarkers; including them would leak the outcome and produce
inflated accuracy for a model that could no longer be used for screening
(the whole point is to work *before* a blood test).

## Design notes

### Calibration

`class_weight='balanced'` and `scale_pos_weight` are **not** used. They rescale
the training distribution to 50/50, which inflates predicted probabilities by
roughly the inverse prevalence ratio. Since the app shows an absolute risk
percentage to a person, that miscalibration is a correctness bug rather than a
tuning choice.

Class imbalance is handled at the **decision threshold** instead
(`tune_decision_threshold`), which selects the operating point that maximises
specificity subject to a sensitivity floor. Ranking quality (ROC-AUC) is
unaffected by re-weighting, so nothing is lost.

Current calibration on the held-out test set:

| Metric | Value |
|---|---|
| Brier score | 0.093 |
| Calibration error | 0.006 |
| Mean predicted risk | 0.137 |
| Observed prevalence | 0.137 |

A reliability diagram is written to
`reports/screening_figures/calibration_reliability_curve.png` on every run.

### Risk tiers

Cut-points are **derived from population prevalence**, not hardcoded round
numbers, and stored in the model package. Because probabilities are calibrated,
the tiers mean something concrete:

| Tier | Rule | Interpretation |
|---|---|---|
| Low | risk < prevalence | below population average |
| Medium | prevalence ≤ risk < 2× prevalence | 1–2× population average |
| High | risk ≥ 2× prevalence | 2× or more population average |

### No training/serving skew

`app.py` contains **no feature-engineering code**. It calls
`build_model_matrix()` from `src/diabetes_screening_model.py` — the same
function the training script uses.

This is enforced, not merely documented. A previous version kept a duplicate
copy in `app.py` which silently drifted (`Age_Band` → `Age_Group`,
`Cardio_Risk_Score` → `Cardiovascular_Risk`); because missing columns were
zero-filled, every served prediction dropped the model's second-largest
coefficient and roughly 4% of users saw the wrong risk tier.
`build_model_matrix()` now **raises** on an unrecognised feature instead of
zero-filling, and `test_serving_parity.py` fails if the two paths ever diverge.

### Known limitation: unused form fields

The web form collects waist circumference, sedentary hours, sugary drink
frequency, processed food frequency, fruit/vegetable intake and family history.
**The current model was not trained on these**, so they do not affect the
result. The UI states this, and `/predict` returns them under `ignored_inputs`
rather than discarding them silently.

## Usage

```bash
pip install -r requirements.txt

# Train (writes model, metrics, reliability curve)
python src/diabetes_screening_model.py

# Verify training/serving parity and calibration
python test_serving_parity.py

# Run the web app
python app.py
```

## Known issues / roadmap

- Age is encoded four ways (`age`, `Age_Risk_Flag`, `Age_Band_*`,
  `Age_BMI_Interaction`), and BMI twice (`Obesity_Flag` and
  `BMI_Category_obese` are the identical column). The resulting collinearity
  makes individual coefficients uninterpretable — `Age_Risk_Flag` currently
  carries a small *negative* weight. Reduce to one encoding per concept.
- `explainability.py` uses group perturbation to the population mean. For a
  linear model, exact contributions are simply `coef × x`; use that or
  `shap.LinearExplainer` instead.
- Precision at the operating point is ~0.32: most flagged users are false
  alarms. Acceptable only if the follow-up test is cheap and low-harm.
- `requirements.txt` is unpinned; `app.run(debug=True)` must not be exposed
  beyond localhost; `/predict` has no input validation or rate limiting.
- No fairness audit. Sensitivity, specificity and calibration should be
  reported separately by sex and age band.
